## 1. 零地址PASS：本次已修正

服务器证据：[timer0.c](../build/rk_review_20261105/server/arch/arm/mach-rockchip/timer0.c)的 `TEST_COMPLETE` 分支固定发送五TLV；[tests.c](../build/rk_review_20261105/server/lib/ddrtest/tests.c)使用零地址作为未发生失败的哨兵。用户本轮明确要求核对零错误地址PASS，新文档也写明该语义。

MCU仍要求完整3/5/7 TLV：5001算法、1017整体FAIL、9002耗时各一次，最多两组相邻9001地址+3001颗粒。

- `9001=0`：该颗PASS，不进入内部 `failures[]`；PC地址输出 `null`。
- `9001!=0`：该颗FAIL，保留完整64位地址；未列出的颗粒沿用PASS约定。
- 1017必须与是否存在非零失败地址一致。整体FAIL但只有零地址、整体PASS却有非零地址均整包拒绝，不能用零地址覆盖矛盾的整体失败。
- 颗粒仅0/1且唯一，**零地址PASS也参与查重**；地址后仍须紧跟对应die。
- CRC、帧宽度、Seq窗口、算法号、单次交付、超时恢复及队列背压保持原有检查。
- 五/七TLV只能说明带一/两组明细，不再直接等同于一/两颗失败；旧四TLV结果仍不接受。

修改位于两板 `App/protocol/rk/frame.c/.h`。PC服务继续消费过滤后的失败数组，JSON字段没有增加；V2 MATS假FAIL保留原作用范围，B1不启用。

限制：这种线上约定不能同时用零地址表达“物理地址0发生真实失败”。若RK将来需测试并上报该地址，必须重新定义合同，不能由MCU猜测。

## 2. 心跳：现有MCU逻辑可复用

证据是 `timer0.c`：解析完接收帧后，无其它回复时发送零TLV或5001+3016进度；`TEST_COMPLETE`在收帧循环之前检查，可以主动上报最终结果。当前 `send_flag` 以一次ISR为作用域，同批有其它应答时可能抑制默认应答，因此不能承诺每一心跳都有独立一对一回复。

MCU每1000ms尝试一次普通心跳，RK空闲应答可用于现有启动ready判断；在途进度仅参考，100也不完成测试。MCU不因收到RK心跳而再回心跳，避免循环。接收继续允许合法窗口内的Seq滞后、重复，不新增自动重发或“3秒没心跳就复位”。B1非ON的收发门禁本次未改。

附件仍有“双向各自1秒发送”、四TLV结果和最小20字节等旧描述；不能整份替换当前16字节零TLV心跳、完整3/5/7结果及Seq规则。

## 3. IDD：已知编码不足以建立完整测量事务

当前证据：[timer0.c](../build/rk_review_20261105/server/arch/arm/mach-rockchip/timer0.c)约443～573行、[spl.c](../build/rk_review_20261105/server/arch/arm/mach-rockchip/spl.c)的 `run_ddr_test_cmd` / 主循环、[idd_test.c](../build/rk_review_20261105/server/lib/ddrtest/idd_test.c)。

仍存在的实际代码问题：

1. 非空闲退出分支 `else if (!action)` 内仍以 `if (action)` 保护恢复函数，因而不会执行真正退出。即使进度回100，也不能证明已恢复DDR状态。
2. IDD进入及时序设置将全局状态置 `TEST_PEND`；主循环仍调用只支持FUNC 1～20的执行表，可能转成“未知命令”及错误最终结果。
3. 进入函数返回值未反映到应答；部分保持循环可直接运行于中断调用路径（例如IDD0），存在后续串口/退出无法推进的风险。IDD4W循环还检查了4R标志。
4. 现有回复是5001+3016进度，忙时255；没有能明确区分进入成功、退出成功、操作失败的可靠合同。不能把255纳入正常0～100进度，也不能把普通FUNC最终包当作IDD操作成功。

MCU后续应接独立阶段：发送进入 → 确认进入 → 稳定 → 有效窗口采样 → 发送退出 → 确认退出 → 0109交付。须明确阶段应答/关联、稳定时长、采样时长、判限、退出失败后的未知状态和恢复方式。当前全程共轨统计不能当成标准IDD窗口；进度100也不能代表IDD电流合格。

本轮复跑已有21～36名称、编号、动作0/1黄金帧及0108/0109门禁回归，未将动作自动接入正式任务、未发送真实IDD命令。原有“仅发编号”的实现保留，但不能据此宣称与这份RK实现兼容完成。

## 4. 时序与启动频率：须分两条事务

运行期时序设置已能从源码确认 `5000(cmd:u16LE) + 701B(value:u32LE)`。PC字段的候选映射如下；这是源码对应关系，尚未批准单位、范围或硬件安全条件。

| PC字段 | RK命令 | 未决/限制 |
|---|---|---|
| CASWriteLatency / CASReadLatency | 0x25 / 0x26 | 数值单位、范围与成功应答待统一 |
| tREFI / tRCD / tRP / tRRD | 0x28 / 0x2B / 0x2C / 0x33 | 单位、范围及生效时点待统一 |
| tRFC | 0x30 `t_rfc_min` | 确认PC语义确为最小值 |
| tRAS | 0x2D最小 / 0x2E最大 | PC只有一字段，不能擅自选其一或同时写入 |
| BurstLength | 0x34 | 当前仅值16返回0，无实际修改 |
| tRC / ODT | 没有对应命令 | 不猜寄存器或换算，不静默丢弃 |
| Freq | 启动查询0x35；运行设置0x27 | `cmd_set_freq()`仍直接返回-1，不能用0x27冒充设置成功 |

运行设置的函数返回值在 `timer0.c` 中被忽略，加上 `TEST_PEND` 混用问题，当前不能从回包证明已设置成功。未来必须逐项确认后才发算法，失败不得继续假称参数已应用；不能把这些配置命令加入FUNC/PARA算法名称目录。

最新启动频率证据：[qfreq.c](../build/rk_review_20261105/server/lib/ddrtest/qfreq.c)及[start.S](../build/rk_review_20261105/server/arch/arm/cpu/armv8/start.S)：

- 实际宏已为 `0x801C`；解析读8字节有符号整数。旧文件头仍写701B/u32、另有801B旧注释，核对时以执行代码为准。
- RK发 `5000/0x35`，查询Seq固定0x35；解析允许回复命令用5000或5001，未核验回复Seq。MCU正式采用哪个容器和关联规则仍须形成明确合同，不能把RK固定查询Seq当作算法结果窗口值。
- 首字节等待200ms，后续字节等待60ms；解析器字节间门限50ms。超过等待后继续启动而不是确认频率应用成功。
- 负数在 `set_freq()` 中保留默认值。非负值直接合入特定Loader地址，没有单位、白名单或完整范围校验；不能凭代码认定PC `Freq`是MHz、MT/s或寄存器原码，更不能默认安全范围。
- `start.S`本次增加 `_query_freq`导出；查询路径源码存在不证明当前板上Loader已经调用或设置生效。

MCU后续需在启动前绑定本轮Freq及默认语义，启动早期仅开放查询/应答所需路径，不能等普通心跳ready才答。B1当前非ON会清解析器并丢RX，可能漏掉早期查询；应单独解决接收窗口、缓存生命周期和应答时限，**本轮不更改供电时序或放宽门禁**。Freq变化后的重启约束、缺省/空串/非法值、SLT路径适用范围及成功确认仍待明确。
